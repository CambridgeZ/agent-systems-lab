# Agent 开发面试补充：36 道工程追问（45—80）

核验日期：2026-11-11。这份清单延续 [基础 44 题](interview-guide.md)，选题依据是官方协议、框架文档与研究中反复出现的工程问题，**不是招聘面试频次统计**。P0 表示建议优先准备，P1 表示有余力时深入。

回答时先讲约束和失败例子，再讲方案、验收和代价。下文的“扩展”是设计题，不表示当前项目已经实现。尤其不要把提供接口、离线脚本通过、真实模型有效和生产可用混为同一件事。

建议先准备 45、48、51—55、59、61、66、68、71、74、75：它们能把工具、长上下文、Skill 加载和执行状态管理串成完整论证。

## 八、结构化调用、协议与 Skill

### 45. [P0] Structured Outputs、JSON mode 和工具参数校验有什么区别？

**回答要点：**合法 JSON 只保证能解析；符合 schema 还约束字段和类型；二者都不能证明路径有权限、金额合理或动作已获批准。Claude 的结构化输出文档分别说明 JSON 输出约束与 strict tool use，具体可用能力还应核对模型与支持的 schema 子集。[官方文档](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

**追问：**参数完全符合 schema，但要求修改测试文件，在哪一层拒绝？

**项目对照：**当前 `tools.py` 有服务端 schema 和业务规则校验；不能据此宣称已启用 provider 的严格约束解码。即使以后启用，执行器检查仍要保留。

### 46. [P0] 模型同时请求多个工具，可以直接全部并行执行吗？

**回答要点：**先判断依赖和副作用。独立读取可并行；“读取版本 → 写入该版本”和“提出补丁 → 验证新文件”必须按因果关系执行。结果要按调用 ID 对应，不能按完成先后随意拼接。工程建议是在执行器中维护依赖与权限，不能从工具名猜测安全性。

**追问：**两个工具写同一个文件，或一个失败另一个成功，最终状态怎么解释？

**项目对照：**当前主循环按批次处理工具，并在产生待审批提案后延后本批次其余工具。并发只读 worker 不等于所有工具都并行。动态依赖调度仍是扩展。

### 47. [P1] 接入几百个工具后，如何降低工具选择错误和上下文成本？

**回答要点：**先给精简目录，再按任务发现并加载相关定义；工具描述要能区分使用场景。目录缓存需要版本、租户权限与失效策略；发现失败时应有明确回退，不能偷偷开放所有能力。Anthropic 的 Tool Search 与程序化工具调用分别针对发现成本和中间数据往返。[官方文章](https://www.anthropic.com/research/advanced-tool-use)

**追问：**工具目录变更后，旧缓存仍返回一个已经撤销权限的工具怎么办？

**项目对照：**当前工具数量少，直接加载目录更易理解。按需 Skill 正文加载不等于已实现平台 Tool Search 或程序化工具调用。

### 48. [P0] 远程 MCP 怎样鉴权？为什么不能把上游 Token 原样透传？

**回答要点：**连接成功不等于有业务权限。应核对资源服务的 token audience、发行方、作用域与用户授权上下文；下游服务也要独立校验。MCP 安全指导明确讨论 token passthrough、confused deputy 和 scope 最小化等风险；不要把“这个工具说自己只读”当成可信授权。[MCP 安全指导](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)

**追问：**用户允许读取仓库，能否顺便借同一个凭证提交代码？

**项目对照：**当前提供本机 stdio 只读 MCP server，没有远程 OAuth、委托授权或凭证代理。把 stdio demo 介绍成远程安全网关是不准确的。

### 49. [P1] 为什么讨论 MCP 时必须先说明协议修订版和 SDK 版本？

**回答要点：**SDK 主版本号和协议修订日期是不同维度。协议演进会改变握手、会话和传输约定；例如 2026-07-28 发布说明介绍了无状态核心，并移除了旧的初始化握手与会话头。旧版教程的时序不能直接套到新版本。[官方发布说明](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

**追问：**升级 SDK 后功能仍能调用，怎样确认没有在兼容模式下掩盖协议差异？

**项目对照：**当前仓库锁定 MCP SDK 1.x，并有实际 stdio 初始化与工具调用测试。升级应单独建立协议契约与迁移测试，不能把本题当作已经迁移的声明。

### 50. [P1] A2A 与 MCP、同进程多 Agent 有什么不同？

**回答要点：**MCP 解决工具与数据接入；A2A 面向独立 Agent 应用之间的发现、消息和任务协作；同进程多 Agent 只是应用内部组织方式。A2A 的 Agent Card、Task、Message、Artifact 等对象解决互操作问题，不会自动提供高质量规划或任务授权。[A2A 规范](https://a2a-protocol.org/latest/specification/)

**追问：**什么时候一个普通内部函数调用就足够，什么时候才值得引入跨服务协议？

**项目对照：**当前双 worker 在本进程内运行，既没有 A2A 服务，也没有跨组织 Agent 互信。协议接入属于扩展。

### 51. [P0] Skill 按需加载以后，为什么上下文仍可能越来越大？

**回答要点：**“延后第一次读取”不等于“正文只占一次预算”。重复调用可能把同一正文反复写入消息；正文更新后，旧摘要还可能继续生效。可设计技能名、内容版本、已加载状态和单次正文预算；命中时返回简短引用，变化时重新验证并加载。渐进披露解决常驻信息规模，不会自动解决生命周期管理。[Anthropic Skills 文章](https://www.anthropic.com/research/equipping-agents-for-the-real-world-with-agent-skills)

**追问：**恢复任务时发现 Skill 文件已修改，应继续用旧版还是新版？

**项目对照：**已实现[元数据发现、章节加载/卸载与版本缓存](../src/agent_lab/skills.py)，runtime 将活动快照和按 call ID 的效果回执持久化；重复加载不增加一份正文，恢复沿用已提交版本。对应[故障与去重测试](../tests/test_runtime_optimization_review.py)，自动执行第三方 Skill 脚本仍属于扩展。

## 九、持久执行与状态一致性

### 52. [P0] LangGraph 的 interrupt 恢复会从那一行接着执行吗？

**回答要点：**不能套用普通函数暂停的直觉。LangGraph 文档说明节点恢复会重新运行节点代码，`interrupt()` 之前的逻辑可能再执行；因此副作用要隔离、幂等化或拆成单独节点。恢复还依赖 checkpointer 与正确的 thread 标识。[官方文档](https://docs.langchain.com/oss/python/langgraph/interrupts)

**追问：**在 interrupt 前发送了一封邮件，用户审批后恢复时怎样避免再发一次？

**项目对照：**当前自建 Runtime 不使用 LangGraph。可以比较本项目 pending 工具批次与图节点重放的差别，但不能声称二者具有相同执行语义。

### 53. [P0] 工具调用状态为什么应单独建账，而不只放在聊天记录里？

**回答要点：**聊天用于模型理解，执行账本用于判断调用是否开始、完成、失败或结果未知。建议绑定 run、调用 ID、工具名、规范化参数摘要和结果版本；恢复时只复用满足条件的已完成结果。读取、写入和外部不可逆动作的缓存策略不同，不能把所有失败都当成可以安全重试。

**追问：**工具已经产生副作用，但结果没落盘就崩溃，账本里该写成功还是未知？

**项目对照：**已实现[调用账本](../src/agent_lab/storage.py)、完整结果先提交、提案操作幂等键与 unknown 恢复策略；[故障注入测试](../tests/test_recovery_integration.py) 验证结果提交后不重复执行。账本不能代替外部服务的幂等键与状态查询，不证明端到端 exactly-once。

### 54. [P0] Worker 有 lease 以后，为什么还可能出现两个执行者同时写？

**回答要点：**旧 worker 可能只是暂停，租约过期后新 worker 接管，旧进程随后恢复。设计上除了过期时间，还可要求每次写入携带单调递增的 fencing token，由持久化或目标服务拒绝旧代次；不能只依赖进程自觉检查。文件、数据库与外部服务分别需要对应边界。

**追问：**网络分区期间，旧 worker 不知道自己已经失去所有权，谁负责阻止它？

**项目对照：**已实现 [`run_leases` + `LeaseWorker` + 单调递增 `epoch` fencing](../src/agent_lab/lease.py)：租约过期后新 Worker 接管会使 `epoch` 加一，滞后恢复的旧 Worker 无论续租、更新 `runs`、登记 `tool_calls`、创建提案还是应用文件补丁都会触发 `StaleEpochError`（见 [`test_lease_fencing.py`](../tests/test_lease_fencing.py)）。当前底层基于单机 SQLite WAL，跨主机部署仍需替换为 Postgres/etcd 共享事务存储。

### 55. [P0] 用户取消任务，为什么不等于已发生的动作全部回滚？

**回答要点：**取消通常是协作式信号；工具可能仍在运行，已经完成的外部副作用不会自动消失。要区分停止后续步骤、等待子任务结束、确认当前操作状态和执行补偿；发邮件等动作甚至不可逆。Temporal 文档也区分 cancellation 与立即 termination，并要求应用自己实现清理或补偿。[官方文档源](https://github.com/temporalio/documentation/blob/main/docs/encyclopedia/workflow/cancellation-and-termination.mdx)

**追问：**取消超时后容器仍活着，怎样清理并防止它再写入？

**项目对照：**当前容器测试有超时清理，未实现完整用户取消协议、Saga 补偿或外部副作用事务。扩展时需要持久取消状态与操作级确认。

### 56. [P1] 图中两个节点同时更新同一字段，如何避免丢失结果？

**回答要点：**先明确字段是覆盖、追加、集合合并还是带版本更新；合并规则必须可预测，不能把字典最后写入者作为默认业务策略。LangGraph 按 state key 使用 reducer，消息也有专门合并语义。[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)

**追问：**并行节点重复提交同一条消息，列表追加会不会制造重复证据？

**项目对照：**当前 worker 结果由主流程汇总，不是任意节点共享可变业务状态。未来引入图框架时要测试并行顺序、重放和重复更新，不只测试正常路径。

### 57. [P1] 动态分解任务后，如何避免 Agent 相互等待或任务无限膨胀？

**回答要点：**任务需要父子关系、依赖、完成条件、局部预算和全局预算；拒绝循环依赖，限制分支深度与并发数。协调者应定义失败策略：部分结果可否继续、何时取消兄弟任务、谁有权重试。以上是工程设计建议，不是多写几个角色提示词就能获得的保障。

**追问：**一个 worker 不断请求再派生 worker，哪一层最终拒绝？

**项目对照：**当前固定 reviewer/tester 两个只读角色，未实现动态 planner 或递归调度。适合用现有共享预算讨论扩展所需的不变量。

### 58. [P0] Checkpoint、上下文摘要、代码快照分别解决什么问题？

**回答要点：**Checkpoint 保存执行位置和状态；摘要保存供下一轮理解的压缩信息；代码快照保存可验证工作成果。三者不能互相替代。恢复时还要核对提案、文件摘要、工具版本和未完成调用，不能仅凭一段“上次已经修好”的摘要继续执行。LangGraph 也区分 thread 内 checkpoint 与跨 thread store。[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

**追问：**摘要说补丁已应用，文件实际还是旧版本，应该信哪一份？

**项目对照：**当前 SQLite 调用账本、分离 HEAD 的 Git worktree（绑定 40 位 `base_commit` 与验证门控提交 [`git_repo.py`](../src/agent_lab/git_repo.py)）和带来源哈希的[结构化工作记忆](../src/agent_lab/working_memory.py)各司其职：审批事实以 `HARNESS_STATE` 为准，工作记忆事实绑定文件或工具结果 SHA-256 并在文件改动后自动降级为 `stale`。

## 十、代码检索、记忆与信任边界

### 59. [P0] 面对百万行仓库，为什么不能只把代码向量化？

**回答要点：**错误码和符号名适合字面量检索；定义、引用与调用关系适合语法/符号索引；概念描述可能受益于语义检索。可先给仓库地图，再逐步读取目标文件和依赖。Aider 的 repo map 就利用符号与依赖关系，在预算内选择相关内容。[官方说明](https://aider.chat/docs/repomap.html)

**追问：**找到同名函数的错误重载、不同语言绑定或生成文件，怎样确认真正调用路径？

**项目对照：**已实现纯标准库 AST 的 [`RepoMapIndex`](../src/agent_lab/repomap.py)（提供 `repo_map` 与 `symbol_search`），按跨文件引用度排序、严格遵守字符预算并按单文件 SHA-256 增量刷新失效文件（见 [`test_repomap.py`](../tests/test_repomap.py)）。它覆盖 Python 静态符号骨架，但仍不等同于多语言 Tree-sitter 或带完整类型解析的 LSP。

### 60. [P1] Agentic RAG 一定比固定检索更好吗？

**回答要点：**Agent 可根据证据不足改写查询、分解问题或补充检索，但多轮会增加成本与错误传播。固定两阶段检索便于控制延迟；有明确多跳依赖时再增加自主查询。工程上应限制轮数，并用同一批标注任务比较召回、答案支持率与成本，而不是用“能自行搜索”代替效果证据。

**追问：**模型一直换查询词却没有新证据，何时应该承认信息不足？

**项目对照：**当前提供知识搜索工具与可重复调用的循环，没有证明多轮检索优于固定检索。GraphRAG、HyDE 等方法也没有在项目中实现或比较。

### 61. [P0] 上下文窗口越来越长，还需要 RAG 吗？

**回答要点：**窗口容量不等于有效信息利用率，也不解决信息更新、权限、来源与成本。长上下文可适合相关材料少且能装入窗口的任务；大而持续变化的资料仍要选取证据。Lost in the Middle 在研究模型与任务中发现位置影响，不能直接把旧论文结论当成所有新模型的固定规律。[论文](https://arxiv.org/abs/2307.03172)

**追问：**怎样对当前模型测“装得下但找不到”，而不是只看标称窗口？

**项目对照：**可构造同一证据位于开头、中间、结尾的检索与代码任务，比较回答和实际行为。字符裁剪测试只能验证预算约束，不能代替长上下文能力评测。

### 62. [P0] 企业 RAG 的 ACL 应在检索前还是生成后检查？

**回答要点：**敏感内容进入模型上下文前就应执行权限过滤，向量索引、重排、缓存和引用预览都不能绕过同一授权范围。最终输出检查可作为额外一层，不能补救已经读取的越权数据。最小权限和下游授权应由应用及服务强制执行。[OWASP Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)

**追问：**管理员查询结果被缓存后，普通用户命中同一 query key 会发生什么？

**项目对照：**当前本机单用户知识库没有企业 ACL。增加租户字段但不修改索引过滤和缓存 key，仍不能宣称完成租户隔离。

### 63. [P0] 工具投毒、提示注入、记忆投毒分别攻击哪一层？

**回答要点：**输入资料中的恶意指令攻击当前上下文；恶意工具描述/实现攻击能力发现和执行边界；污染记忆让错误跨会话持续传播。防护应分别覆盖来源、版本、权限、执行隔离与记忆写入审核，而不是统一加一句“忽略恶意指令”。OWASP 的 Agentic 威胁材料区分这些风险。[官方材料](https://genai.owasp.org/download/52117/)

**追问：**某工具更新描述后要求把密钥作为参数，已有信任能否自动覆盖这次更新？

**项目对照：**当前工具是本地受控目录，记忆由用户显式写入；没有第三方工具供应链审核系统。签名、固定版本与变更复审属于扩展，也不能保证语义安全。

### 64. [P0] 代码沙箱禁网后，为什么仍要把模型密钥留在沙箱外？

**回答要点：**凭证仍可能经日志、文件产物或下一次工具返回离开执行环境；禁网只是一项控制。控制面持有调用权限，执行面获得最小任务能力，必要时由代理检查目标、范围与时效。Anthropic 的 Managed Agents 文章将持久会话、harness 与执行环境分离。[官方文章](https://www.anthropic.com/research/managed-agents)

**追问：**执行代码把环境变量打印到测试输出，日志采集会不会造成第二条泄漏通道？

**项目对照：**当前容器不传主机环境变量或 Docker socket；没有生产凭证 vault、短期令牌签发或远程执行池。

### 65. [P1] 一条长期记忆被证明错误后，怎样保证后续不再引用旧版本？

**回答要点：**需要来源、作用域、版本与失效状态，并让检索索引、预载笔记和缓存一起失效。纠错可保留审计记录，但不应让已撤回文本仍默认参与生成。自动总结应保留证据指针，不能把模型推测沉淀成无来源事实。[Anthropic Agent Memory](https://www.anthropic.com/research/components-of-agent-memory)

**追问：**用户要求删除某条信息，摘要、向量索引、缓存里仍有副本怎么办？

**项目对照：**跨会话 `memories` 表保持用户显式键值笔记；任务内[结构化工作记忆](../src/agent_lab/working_memory.py)则强制校验每条 `fact` 引用的文件或 `tool_calls` SHA-256，并在目标文件被补丁修改后自动将旧事实标为 `stale`（`file_hash_changed`，见 [`test_working_memory.py`](../tests/test_working_memory.py)）。跨会话记忆的向量索引级撤回传播仍属于扩展。

## 十一、代码 Agent 的评测与观察

### 66. [P0] SWE-bench 分数衡量的是模型，还是整个 Agent 系统？

**回答要点：**结果受到模型、提示、harness、工具、采样预算与运行环境共同影响。官方评测把补丁应用到仓库后运行测试；必须同时报告所用设置。还要分开 resolved、测试未通过和环境错误，不能把没有完成评测的实例悄悄排除。[SWE-bench 评测指南](https://www.swebench.com/SWE-bench/guides/evaluation/)

**追问：**CPU/内存不同，或一个系统允许更多尝试，排行榜百分比可以直接比较吗？

**项目对照：**除 10 个控制流回归外，已新增 5 任务编码基准 [`model_evals.py`](../src/agent_lab/model_evals.py)（[`data/evals/coding_benchmark/`](../data/evals/coding_benchmark)），在独立 Git worktree 与受限 Docker 容器中运行真实单测、支持有界修复回环，并严格拆分 `model_failure` 与 `infrastructure_failure`。无外部密钥时 `--provider reference` 显式标记 `benchmark_harness_verification_only`（见 [`model-eval-sample.json`](model-eval-sample.json)），绝不冒充真实 LLM 成绩。[Anthropic 研究](https://www.anthropic.com/research/infrastructure-noise)

### 67. [P1] 怎样减少训练数据污染、公开补丁泄漏和 grader 过拟合？

**回答要点：**划分训练/调参/保留任务，固定仓库版本，并检查评测环境能否访问目标补丁。新增近期、不同仓库任务有助于扩大覆盖，但不能证明绝对无污染。SWE-bench-Live 提供持续更新的任务构建研究，其“更能抵抗污染”也不等于所有分数差异都由污染导致。[论文](https://arxiv.org/abs/2505.23419)

**追问：**改动只对公开样例有效，如何发现它没有修复真实需求？

**项目对照：**内置折扣 bug、修复和测试都是公开合成例子，应介绍成工程回归。真正模型评估需要额外未见任务、独立验收和失败分析。

### 68. [P0] LLM-as-a-judge 有哪些偏差？怎样校准？

**回答要点：**常见风险有位置、冗长、自偏好与推理能力不足。可以制定具体 rubric、盲化系统身份、交换候选顺序、用人工标注集测一致性；代码行为优先用可执行验收。更强的 judge 也不是事实真值。MT-Bench 研究讨论了这些偏差。[论文](https://arxiv.org/abs/2306.05685)

**追问：**同一对回答交换顺序就改变胜者，应怎样统计而不是只挑有利的一次？

**项目对照：**当前有确定性最终状态检查和受限算术 grader，没有训练或验证 LLM judge。加入 judge 后要单独报告与人工、执行结果的分歧。

### 69. [P0] 上线以后，怎样做持续评测而不泄漏真实用户数据？

**回答要点：**离线保留任务做回归，线上按权限采样并脱敏，以小流量灰度观察任务结果、工具错误、成本和长尾延迟；人工判断与确定性评分互相补充。失败轨迹应能转成新测试，同时保留原始验收标准，避免为追分改变定义。Anthropic 的 evals 文章强调任务、轨迹、评分器和最终结果的区分。[官方文章](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

**追问：**新模型回答更流畅，但代码验收下降、用户点击率上升，能否发布？

**项目对照：**当前有本机事件和离线回归，没有线上采样、A/B、灰度或用户反馈数据；不应写线上提效比例。

### 70. [P1] Agent 轨迹怎样接 OpenTelemetry？为什么不应直接记录所有 prompt？

**回答要点：**把一次任务、模型调用、工具调用和检索组织成有父子关系的 span，关联 run、调用和错误，保留耗时及资源计量。敏感内容应最小化采集、脱敏并限制保留；token 不要在父子层重复累计。GenAI 语义约定仍会演进，采用时需锁定版本与字段含义。[官方仓库](https://github.com/open-telemetry/semantic-conventions-genai)

**追问：**两个 worker 的模型用量已经汇入主任务，再累加所有 span 会不会重复算账？

**项目对照：**当前 SQLite 事件不是完整 OTel tracing。可以映射现有事件，但跨服务 trace propagation、采样与日志访问控制仍需实现。

## 十二、性能、预算与上下文优化

### 71. [P0] Prompt caching 怎样设计，为什么不只是“缓存整个请求”？

**回答要点：**模型前缀缓存利用稳定前缀；应用结果缓存复用已经得到的结果，二者失效和权限规则不同。工程上可将稳定系统指令、工具目录放在前部，把动态任务和结果放在后部，并记录命中/写入用量。实际模型、最小长度、TTL 和计费要查平台文档，不能照搬固定比例。[Claude Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

**追问：**工具 schema 顺序或系统指令变了，缓存命中与行为会怎样变化？

**项目对照：**不要把本机 Skill 内容缓存、工具结果账本称为模型 KV cache。当前 provider 是否启用远端 prompt cache，应以请求参数和 usage 实测为证。

### 72. [P1] 大小模型路由该怎样做，为什么不能只相信模型自报“我有 90% 把握”？

**回答要点：**用带结果标签的任务评估路由特征和阈值，在质量、成本与延迟之间选工作点；失败或低置信请求可升级模型。自报分数必须经过校准，不能天然当概率。RouteLLM 研究使用偏好数据学习强/弱模型之间的路由，但它的结果不能直接当成本项目收益。[论文](https://arxiv.org/abs/2406.18665)

**追问：**把模型或业务分布换掉，旧阈值是否还可信？

**项目对照：**当前 provider 是显式配置，没有大小模型路由或校准数据。可先用相同未见任务建立单模型基线，再评估路由。

### 73. [P1] 首字延迟、总完成时延和流式事件有什么不同？

**回答要点：**流式文本可改善用户等待感，但不能消除检索、排队、工具和验证耗时。应拆开队列、首字、生成、工具与人工等待，并看 p95/p99；不能只展示一条很快的 demo。长任务还应及时提供可观察进度，而不是伪造百分比。

**追问：**用户看到第一段解释很快，但补丁要一分钟才出来，这算性能优化成功吗？

**项目对照：**当前 SSE 是执行事件流，不是 Claude token 流。引入模型文本 streaming 后也要等待完整工具参数并校验，不能执行尚未结束的 JSON 片段。

### 74. [P0] 怎样控制共享预算，为什么响应后统计 token 还会超支？

**回答要点：**多个 worker 可能同时看到余额，必须在发起前预留额度，结束后按实际 usage 对账，并定义失败重试的计量。响应后检查只能阻止下一次调用；硬费用上限还依赖输入估算、价格版本和服务端保障。限步数、限输出与计费预算是不同控制。

**追问：**两个并发请求各自未超额度，合计却超预算，责任在 provider 还是调度器？

**项目对照：**当前有共享调用预算与响应 usage 记录，但不能据此承诺严格金额上限。扩展验收应模拟并发预留、请求失败、取消与余额归还。

### 75. [P0] 长上下文怎样优化，才能少花 token 又不破坏执行事实？

**回答要点：**区分持久完整记录、模型当前窗口与按需取回的证据；优先减少重复 Skill/工具正文，对旧结果给出摘要与可查询标识；裁剪时保留完整调用/结果组、当前目标、待审批对象和最新关键证据。摘要是派生数据，不能替代调用账本或批准记录。[上下文工程文章](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

**追问：**压缩后模型忘记了审批已经被拒绝，会不会重新提出同一副作用？

**项目对照：**已实现 system/tools/messages JSON 字符预算、原子组裁剪、固定审批/Skill 状态、大结果投影和 tool_result_get 分页；[专项说明](context-skills-state.md) 有实验与局限。当前没有模型语义摘要。优化效果需同时测上下文体积与任务验收，不能只报告压缩率。

### 76. [P1] 加一个 Critic / Evaluator Agent，就能可靠地自我纠错吗？

**回答要点：**相同模型、相同证据和相同错误假设会产生相关错误。独立角色有助于检查，但应给不同目标、外部验收与有限修订预算；不能让生成者和评价者相互说服后替代测试。工程建议先把可执行条件确定化，再评估模型评价补充了什么。

**追问：**Critic 说测试不合理，Generator 建议改测试，谁有权改变验收条件？

**项目对照：**当前 tester worker 仅给只读建议，确定性 grader 位于外部。没有证明双角色比单模型更准确，更没有让 worker 自主批准补丁。

## 十三、训练、推理与综合设计

### 77. [P1] SFT、DPO、RL 和改 harness 分别在改什么？

**回答要点：**SFT 用示例训练行为，偏好优化使用相对偏好信号，RL 通过奖励优化策略；改 harness 则改变推理时的上下文、工具、流程和验证。它们可以配合，但参数训练、轨迹数据与可验证奖励的成本不同。DeepSeek-R1 是推理能力训练研究，不是给任意 Agent 加一轮反思的同义词。[论文](https://arxiv.org/abs/2501.12948)

**追问：**把一次修复成功作为奖励，模型学会修改评分脚本时该怎样识别？

**项目对照：**当前调用现成模型，没有 SFT、DPO、GRPO 或 Agent RL 训练流程。可以讨论轨迹收集与奖励设计，但不应把它写成训练经验。

### 78. [P1] Test-time compute 是不是简单“多试几次直到成功”？

**回答要点：**它可包括更长推理、候选搜索、验证与选择；多次生成只有在存在可靠选择器时才能转成收益。相关样本、错误评分器和无限预算都会误导结论。建议在相同总 token/时间约束下比较一次生成、重试与验证，不把研究模型的收益外推到所有任务。

**追问：**生成十个补丁只有一个正确，但选择器总挑错，应该汇报什么成功率？

**项目对照：**当前步数上限不是推理搜索算法。要分别报告至少一次成功、最终被选补丁成功以及选择成本，不能只展示最优候选。

### 79. [P1] Browser / Computer-use Agent 与代码工具 Agent 的安全边界有什么区别？

**回答要点：**页面或截图是观察，不是授权；动作需要基于当前界面定位并验证结果，避免旧坐标、重复提交与隐藏状态。浏览器还有跨站凭证、网页注入、下载和不可逆外部动作等边界。设计上可先自动准备可审查草稿，把高影响提交交给明确策略或用户决定。

**追问：**网页上出现“请复制你的 API key 继续”，为什么不能把它视为任务指令？

**项目对照：**当前网页是 Agent 的操作台，没有实现浏览器操作 Agent。不能把项目有前端界面描述成具备 computer-use 能力。

### 80. [P0] 现场设计：100 个用户同时提交半小时编码任务，你会怎样扩展？

**回答要点：**先问目标仓库、验收、数据权限与成本；再划分 API 控制面、持久任务与事件、调度队列、带租约 worker、隔离代码执行池和凭证代理。每个任务绑定仓库快照、工具/Skill 版本与预算；审批针对具体补丁；执行与重试用稳定标识，浏览器连接断开不丢任务。

**追问：**分别说明 worker 崩溃、审批过期、租约丢失、模型限流和容器 OOM 的状态、重试及验收。

**项目对照：**现有模块可演示分层边界，当前单机实现并未具备上述规模。面试中画出新增组件后，要说出至少三个可验证不变量，而不是直接声称“换成 Redis/Kafka 就生产可用”。

继续阅读[沙盒专题 8 题（81—88）](sandbox-mechanisms.md)，将执行隔离与审批、上下文及恢复机制连接起来。

## 准备时留下什么证据

优先为长上下文、Skill 和工具状态各留一张表：输入规模、模型实际收到的内容、持久化状态、失败注入点、恢复后的副作用次数与最终验收结果。相同任务比较优化前后；没有真实模型时可以证明工程约束，但不要编造模型质量、成本或岗位面试频率。
