# 并行研究与多 Agent 的边界

本笔记为原创的代码开发场景分析。
阅读背景：[How we built our multi-agent research system](https://www.anthropic.com/research/multi-agent-research-system)。

## 适合并行的任务

理解公开接口、阅读测试和分析安全约束可以由不同只读工作者同时完成。每个
工作者接收清楚的目标、输入范围、结果格式与预算，然后将简短证据返回协调者。
如果下一项分析必须依赖上一步修改结果，则不能为了展示多 Agent 而强行并行。

## 共享状态带来的冲突

两个工作者同时修改一个文件会发生丢失更新；同时批准同一提案会造成重复写入。
项目把并行限制在分析阶段，将写入集中到具有比较后交换校验的审批链路。生产
可以使用隔离 worktree、任务锁或事务队列，但仍要设计冲突解决和回归验证。

## 工作流与自主协调者

固定的“代码视角”和“验证视角”两路分析是并行工作流。只有协调者根据任务动态
决定如何拆分、分配和停止时，才更接近自主 orchestrator-workers。不要把多个
异步函数简单地称为完整自主多 Agent 平台。面试中应说明实际实现的控制流。

## 衡量并行是否值得

比较相同任务集下的成功率、总 token、工具量、墙钟耗时和冲突次数。共享较多
背景会增加重复 token，摘要又可能丢失细节。没有任务重复试验，就不能仅凭某次
演示速度宣称多 Agent 提高了整体效果。简单修复通常从单 Agent 开始更容易解释。
