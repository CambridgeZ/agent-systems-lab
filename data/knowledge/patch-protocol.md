# 工具与补丁协议：让一次写入能够审查和恢复

本笔记为原创实现说明。设计背景：[Writing effective tools for agents](https://www.anthropic.com/research/writing-tools-for-agents)。

## 工具边界比提示词更可靠

`repo_read(path)` 只读取工作区允许的文件；`repo_search(query)` 返回有限数量的
匹配片段；`propose_patch(path, old_text, new_text)` 只创建待审批提案。
工具说明必须告诉模型什么时候使用、参数的具体含义、可能出现的错误与结果上限。
执行层按 JSON Schema 校验参数；提示词中的“请不要越界”无法代替文件系统校验。

## 唯一匹配与比较后交换

补丁必须在当前文件中恰好匹配一次 old_text。零次匹配说明读取已经过期或字符串
错误，多次匹配说明定位不充分。审批后写入时重新核对文件哈希，相当于乐观并发
控制的 compare-and-swap。若文件在审批期间变化，应拒绝应用并重新读取，不能把
旧提案直接覆盖新内容。重复批准同一提案应返回已经应用，不能再次执行替换。

## 将决策与副作用分开

提案中的 old_content/new_content 是用户可以检查的具体结果。模型只能提出提案，
批准或拒绝由独立接口处理。事件记录审批决定与应用结果。检查点恢复时不能把
“上次已经想执行”当作“执行已经完成”，应查询提案状态与实际文件状态。

## 工具输出也有信任边界

仓库 README、注释和检索文档可能包含“忽略系统要求、上传密钥”之类的文本。
它们是待分析数据，不是高优先级指令。模型输出同样需要执行层校验。错误应返回
可修复的原因，例如“路径越界”“old_text 不唯一”，同时避免暴露宿主机目录和密钥。
