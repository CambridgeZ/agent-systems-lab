# 代码执行、安全隔离与审批

本笔记为原创的项目威胁边界说明。
阅读背景：[Claude Code sandboxing](https://www.anthropic.com/research/claude-code-sandboxing)。

## 路径和命令边界

工具接收相对路径，并拒绝目录穿越、绝对路径与符号链接越界。补丁限制在允许的
Python 文件内。工具没有任意 shell 参数，模型不能把“运行测试”解释为执行任意
宿主机命令。不要把路径校验误称为操作系统沙箱：它无法隔离被执行程序的系统调用。

## 静态检查与执行代码

`ast.parse` 仅解析源码，不导入模块，也不执行生成代码。运行测试则会执行仓库
代码；即使命令本身固定，测试内容也可能恶意。项目只允许在显式启用的 Docker
环境中执行这一步，禁用网络、限制资源、去除额外能力，且不给容器宿主机 socket。
Docker 不可用时应报告无法执行，不能静默改成宿主机 Python 运行。

## 审批不是隔离

人工批准表示同意具体补丁，不保证补丁安全，也不授予无限文件和网络权限。写入
依然要通过路径范围、唯一匹配和文件版本检查。审批决定应绑定 run_id 与 proposal_id，
模型工具集中不应提供“批准自己的提案”接口。

## 凭证与外部输入

API 密钥只由服务端从环境读取，不进入仓库、浏览器响应或提示词。仓库注释、
工具输出和 Skill 正文都不能提升为系统策略。完整生产平台还需要认证、授权、
隔离凭证代理、安全更新和审计；本地演示只展示有限的防护机制。
